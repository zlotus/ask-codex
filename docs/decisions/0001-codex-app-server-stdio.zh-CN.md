# ADR 0001：通过 JSONL stdio 使用 Codex app-server

- 状态：已接受
- 决策日期：2026-07-21
- 追溯记录日期：2026-07-23

## 背景

Ask Codex 需要访问 Codex 原生线程、流式轮次和条目、审批、模型以及账户状态。封装终端 UI 会使应用与展示文本耦合。依赖 Codex Desktop 的私有 IPC，则会依赖未文档化的接口和桌面端打包方式。另行维护一套会话模型，会使浏览器中的历史记录与其他 Codex 客户端产生分歧。

有文档支持的 `codex app-server` 协议提供了所需的客户端能力。它的 WebSocket 传输仍处于实验阶段，而基于 stdio 的 JSONL 让 Ask Codex 能够把进程和凭据留在可信主机上，并置于自身网关之后。

## 决策

将 `codex app-server --listen stdio://` 作为子进程启动，并通过以换行符分隔的 JSON-RPC 消息进行通信。以 Ask Codex 客户端身份对其初始化，仅向浏览器开放另行治理的协议子集。

将当前安装的 Codex CLI 所生成的绑定视为协议事实来源。每当 CLI 发生变化时，比较相关的请求、响应、通知和联合类型结构，并在同一次变更中更新规范化逻辑和聚焦测试。

## 影响

- 线程保持为 Codex 原生线程，可在受支持的 Codex 客户端之间继续使用。
- 凭据和 Codex 进程留在主机上，而不是进入浏览器。
- 网关必须可靠地转换生命周期、请求、响应、错误和流式行为。
- 由于 app-server 接口会演进，CLI 升级可能要求协议与 UI 协同变更。
- Ask Codex 不会自动继承终端 UI 或 Codex Desktop 的行为。

## 考虑过的替代方案

- 解析或嵌入 Codex 终端 UI：拒绝，因为这会暴露终端界面，并使行为与面向人的输出耦合。
- 依赖 Codex Desktop 私有 IPC：拒绝，因为它没有文档支持，并会使项目与私有应用边界耦合。
- 维护 Ask Codex 会话数据库：拒绝，因为这会重复 Codex 的线程状态，并削弱跨客户端连续性。
- 让浏览器直接连接 app-server WebSocket 传输：目前拒绝，因为策略执行和远程访问控制需要网关。
