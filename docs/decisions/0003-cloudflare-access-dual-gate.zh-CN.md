# ADR 0003：使用彼此独立的 Cloudflare Access 与应用令牌关卡

- 状态：已接受
- 决策日期：2026-07-21
- 追溯记录日期：2026-07-23

## 背景

本项目需要从包括移动浏览器在内的其他设备上使用，而 Codex 进程运行于一台常开主机。直接发布网关会暴露一项服务：它能以操作系统用户身份读取文件、修改工作区、运行沙箱命令并请求更广泛的权限。

Cloudflare Tunnel 可以使服务保持在环回接口上，Cloudflare Access 则可以强制执行身份验证与 MFA。边缘身份策略与应用凭据保护的是不同边界，二者都不应在无提示的情况下取代另一个。

## 决策

对于使用 Cloudflare 主机名的部署：

- 让 Ask Codex 保持绑定于 `127.0.0.1`，并将隧道路由到该环回服务；不要开放路由器入站端口，也不要绑定到公共接口。
- 要求采用带 MFA 的精确用户 Cloudflare Access 策略。
- 只要配置了 `ASK_CODEX_PUBLIC_ORIGIN`，就要求提供独立的高强度 `ASK_CODEX_TOKEN`。
- 在第一条消息帧中验证 WebSocket 客户端。绝不能把令牌放入 URL，也不能将其转发给 Codex、MCP 服务器、hook 或命令。
- 只接受一个配置好的精确公共 origin，并要求代理保留公共 `Host` 请求头。
- 将 Codex 人工审批保留为第三道独立的执行关卡。

Cloudflare 是一种受支持的部署选项，而不是强制性的产品依赖；配置正确的 VPN 或 SSH 隧道仍然有效。

## 影响

- 隧道部署不需要在主机上开启公共监听器。
- 远程访问会在不同阶段分别依赖 Cloudflare 身份、应用令牌和 Codex 审批。
- 运维人员必须保护两种不同的令牌：cloudflared 连接器令牌和 Ask Codex 应用令牌。
- 把公共 `Host` 替换掉或使用不精确 Origin 的代理改写会默认失败，并要求修正配置。
- Access 失效或单个令牌泄露本身不会移除所有关卡，但仍需立即调查并轮换凭据。

## 考虑过的替代方案

- 将 Ask Codex 直接绑定到公共接口：拒绝，因为这会无谓地暴露应用和主机网络。
- 在没有应用令牌的情况下信任 Cloudflare Access：拒绝，因为代理和 Access 配置位于应用边界之外。
- 只在公共监听器上使用应用令牌：拒绝，因为它缺少边缘身份、MFA 和隧道隔离。
- 将令牌放入查询参数：拒绝，因为 URL 通常会出现在浏览器历史、日志、截图和中间方遥测中。
