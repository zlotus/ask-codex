# ADR 0022: Replace prompt-free turns with sandbox-aware auto-run

- Status: Accepted
- Decision date: 2026-08-09
- Supersedes: [ADR 0020](0020-one-turn-prompt-free-approval.en.md), [ADR 0021](0021-first-turn-one-shot-prompt-free-approval.en.md)
- Amends: [ADR 0002](0002-security-gateway-and-manual-approval.md)

## Context

ADR 0020 and ADR 0021 implemented a per-turn prompt-free mode with
`approvalPolicy: "never"`. That policy does not widen the sandbox, but it also
does not produce boundary-crossing approval requests for the user to handle.
Operations such as writes outside the workspace or restricted network access
can only fail. The product needs a different automation boundary: actions
already allowed by the active sandbox should run automatically, while requests
to cross that boundary must still go to the user.

The stable `AskForApproval` generated by Codex CLI 0.147.0 with
`codex app-server generate-ts` without `--experimental` includes `untrusted`
and `on-request`. [OpenAI's official sandbox and approval combinations](https://learn.chatgpt.com/docs/agent-approvals-security#common-sandbox-and-approval-combinations)
define `untrusted` as automatically running only known-safe operations and asking
before untrusted commands. `on-request` automatically runs operations allowed
inside the current sandbox while still asking for writes outside the workspace,
restricted network access, and other boundary crossings. Both policies can keep
the reviewer fixed to the user.

## Decision

- Thread creation, thread resume, native fork, and cross-device queue
  consumption remain fixed to `approvalPolicy: "on-request"` and
  `approvalsReviewer: "user"`. Steering carries no approval policy.
- Every ordinary direct `turn/start` explicitly uses
  `approvalPolicy: "untrusted"`. If the browser omits the field, the gateway
  also rebuilds it as `untrusted`, making strict mode the fail-closed default.
- On an existing idle thread or a new-thread draft with configured cwd and
  sandbox, the user may explicitly arm one sandbox-aware auto-run turn. That
  turn uses `approvalPolicy: "on-request"`, while the gateway still injects
  `approvalsReviewer: "user"`. Actions allowed inside the sandbox run
  automatically; sandbox escalation, writes outside the workspace, and
  restricted network requests still require user approval.
- The gateway accepts only `untrusted` or `on-request` for direct
  `turn/start`. Browser-supplied `never`, structured `granular`, reviewer, or
  unknown approval values are rejected. A capability's presence in the mature
  schema does not implicitly add it to the product security model.
- The one-shot choice remains only in current-page memory and does not persist
  or cross threads, pages, or devices. It cannot change while Working or
  sending and clears after completion, cancellation, failure, an invalid start
  result, or failed thread creation or turn start. Queue operations and
  steering neither read nor consume it.
- The implementation does not use experimental `thread/settings/update`, the
  app-server WebSocket transport, or another experimental API. Unsupported
  granular `request_permissions` and MCP elicitation continue to fail closed.
- Ask Codex does not send an automatic write after completion to reset upstream
  settings. The next ordinary direct turn explicitly carries `untrusted`;
  creation, resume, fork, and queue operations continue to carry their fixed
  `on-request` policy.

## Rationale

Defining a non-critical action as one already allowed by the active sandbox
reuses Codex's mature execution boundary. It avoids asking the browser or
gateway to infer risk from command text, tool category, paths, or model-provided
reasons. `untrusted` and `on-request` form meaningful stable tiers: the former
adds stricter command review, while the latter reduces interruptions for
routine sandboxed work without removing human review at the boundary.

## Consequences

- A one-shot auto-run turn no longer fails merely because an operation needs a
  sandbox escalation. Standard command and file-change approvals still appear
  in the browser through the existing owner route.
- Ordinary direct turns may prompt more often than the former `on-request`
  default. That is the intended effect of the stricter default.
- A compromised authenticated browser can at most select `on-request` for a
  direct turn and can no longer suppress approval prompts. The gateway still
  does not treat that browser choice as a sandbox permission grant.
- After an auto-run turn and before the next explicit Ask Codex write, the
  upstream thread setting may remain `on-request`. This UI does not guarantee
  another Codex client's behavior in that window, but sandbox-boundary approval
  is not disabled as it was under `never`.
- UI text must describe sandbox-aware auto-run and must not call the control
  prompt-free or imply that escalations are automatically approved.

## Alternatives Considered

- Keep `never` and reconstruct approvals in the gateway: rejected because the
  app-server emits no approval request for the gateway to intercept under
  `never`.
- Use `on-request` for every direct turn and remove the control: viable but not
  adopted because it removes the accepted per-turn strict/auto choice.
- Automatically approve by tool category or command text in the gateway:
  rejected because those signals do not reliably express path, environment,
  and actual impact.
- Use stable `granular`: not adopted because a disabled category is
  automatically rejected, not automatically approved.
- Use `approvalsReviewer: "auto_review"`: not adopted because it replaces the
  human reviewer for sandbox-boundary requests.
- Reset settings after each turn through an experimental RPC: rejected because
  the project uses only mature app-server APIs and the extra write changes
  ownership and recovery semantics.
