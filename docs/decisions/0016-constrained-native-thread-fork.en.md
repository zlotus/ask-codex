# ADR 0016: Expose constrained native thread fork

- Status: Accepted
- Decision date: 2026-08-06

## Context

The experimental schema generated by Codex CLI 0.146.0 includes `thread/fork`.
Its request can locate the source by `threadId` or an unstable rollout `path`,
and can specify cut points, model, cwd, permissions, instructions, and other
runtime overrides. The response returns the new thread, inherited settings, and
`thread.historyMode`.

Passing these fields through would let the browser choose host paths and
permissions and would bind unsupported history truncation, rollback, or detached
review semantics into the client. Complete history can also make the fork
response exceed the gateway message limit. Fork is a persistent write without
an idempotency key, so a disconnect or timeout cannot prove that no new thread
was created upstream.

## Decision

- The browser may submit only the source `threadId`. The gateway rebuilds the
  request field by field and fixes `approvalPolicy: "on-request"`,
  `approvalsReviewer: "user"`, and `excludeTurns: true`. It rejects `path`, cwd,
  model, permissions, instructions, cut points, and all other overrides.
- The gateway strictly validates that the new ID differs from the source,
  `forkedFromId` exactly matches the source, the response and thread cwd are the
  same absolute path, history mode is `legacy` or `paginated`, approval settings
  remain user-owned, sandbox type is known, and excluded `turns` are empty. It
  projects only UI-required thread metadata and effective settings, excluding
  rollout paths, instruction sources, runtime workspace roots, and unknown fields.
- Only a structurally valid success synchronously assigns the new thread owner
  to the requesting connection. The source owner remains unchanged. Failure,
  malformed results, ID collisions, Codex errors, or requester disconnects do
  not change ownership.
- The client offers an explicit Fork action only for an idle source. It normally
  selects the new thread and reads history through the existing bounded
  `thread/turns/list` path. If the user changes selection while the request is in
  flight, it updates the list without taking selection back. Default and
  paginated histories retain the persistence contract returned by app-server;
  the client neither selects nor migrates the mode.
- On success, bounded in-process structured Plan records are copied from the
  source to the new thread ID. File-download authority is established only from
  the authoritative new-thread cwd in the fork response, never from a
  browser-provided scope.
- Fork is never retried automatically and is not bundled with rollback,
  detached review, or arbitrary history truncation.

## Consequences

- Default and `paginated` sources share one fork and history recovery flow, and
  long history is not embedded in the initial RPC response.
- Fork gives the browser no new path, permission, or configuration injection
  surface, and does not override an inherited external sandbox.
- An unknown result after disconnect can leave an app-server-created thread that
  was not automatically selected. The user can refresh the list to confirm it;
  the client will not risk a duplicate fork by replaying the request.
- Current validation uses the CLI 0.146.0 generated schema and deterministic
  policy, ownership, pagination, and UI tests. No real `thread/fork` was invoked
  solely for verification because that would create a persistent test thread.

## Alternatives Considered

- Return complete fork history: rejected because long threads can exceed the
  message limit and the project already has a bounded pagination path.
- Expose cut points or rollout paths: rejected because that expands product
  semantics and the host-path attack surface.
- Call `thread/resume` after fork: rejected because a successful fork already
  creates the thread and returns its settings; another resume would needlessly
  change ownership again and widen the unknown-result window.
- Retry after timeout or disconnect: rejected because `thread/fork` has no
  idempotency key.
