# ADR 0015：显式且绑定活跃轮次的文本 steering

- 状态：已接受
- 决策日期：2026-08-05
- 扩展：[ADR 0002](0002-security-gateway-and-manual-approval.zh-CN.md)、[ADR 0012](0012-read-only-connection-recovery.md)

## 背景

Codex CLI 0.146.0 提供原生 `turn/steer`，允许用户在一个轮次仍在运行时补充输入。请求必须
同时携带 `threadId`、`expectedTurnId` 和 `input`，响应返回实际接收 steering 的
`turnId`。如果浏览器只根据“当前有运行中轮次”发送，而不把请求固定到确切轮次，轮次在
点击发送与请求处理之间结束或切换时，输入可能被错误地交给另一轮。

Steering 也是有实际影响的写操作。断线或超时后，浏览器不能判断 Codex 是否已经接收输入；
自动重放可能重复指令。多浏览器同时查看同一线程时，成功 steering 后产生的审批也需要有
明确 owner。

## 决策

- 仅在用户明确提交且所选线程存在活跃 `inProgress` 轮次时调用 `turn/steer`。提交时捕获
  该轮次 ID，并同时作为 `expectedTurnId` 和本次未确认提交的身份；请求进行期间后续输入
  保持为独立草稿。
- 第一版 steering 只接受一个非空文本输入项。运行中不上传图片，也不提交 `cwd`、模型、
  reasoning effort、sandbox 或其他轮次设置；图片入口以及模型和 effort 控件保持禁用，
  中断按钮继续可用。
- 网关把 `turn/steer` 列入显式 allowlist，并逐字段重建参数。它只接受
  `threadId`、`expectedTurnId` 和文本 `input`，拒绝未知字段、宿主机路径、设置覆盖、
  非文本输入和畸形或超限内容。
- 网关只向浏览器投影 `{ turnId }`，并要求返回的 `turnId` 与已清洗请求中的
  `expectedTurnId` 精确一致。缺失、畸形或不匹配的响应失败关闭，不能作为已确认提交。
- `turn/steer` 与同线程的 `thread/resume`、`turn/start` 一起串行。只有上游返回结构有效且
  匹配预期轮次的成功结果后，请求浏览器才成为该线程的审批 owner；失败、断线、Codex
  error 或结果未知都不得改变 owner。结果未知时，同线程中已排队的 ownership 写操作按既有
  规则取消。
- 只有收到匹配响应后，界面才移除该次未确认输入。失败输入与发送期间形成的新草稿分开保留；
  只有原轮次仍是当前活跃轮次时才允许显式重试，并继续使用原来的 `expectedTurnId`。
- 连接恢复、只读重同步和页面重载绝不自动重放 `turn/steer`。结果未确认时由用户决定是否在
  仍活跃的原轮次中重试，或将内容作为后续新轮次重新编辑提交。

## 理由

`expectedTurnId` 是协议提供的并发保护，应由浏览器和网关共同保留，而不是依赖易变化的
“当前轮次”状态。严格的文本范围让首版复用现有输入体验，同时避免为运行中附件生命周期和
设置语义作未经验证的假设。把确认、owner 和不重放规则与其他 ownership 写操作对齐，可以
在多客户端和连接故障下保持一致的审批与幂等边界。

## 影响

- 用户可以在 Codex 工作时追加文字，不必先中断轮次或等待其完成。
- 如果轮次在请求处理前已经结束，steering 会明确失败，而不会自动成为一个新轮次或进入另一
  个活跃轮次。
- 网络结果未知时可能需要用户手动判断并重新组织输入；这是避免重复 steering 的显式取舍。
- 运行中图片和下一轮设置仍不可用。未来开放它们前，必须重新核对 app-server schema、附件
  所有权和一次性消费语义。

## 考虑过的替代方案

- 将运行中输入排队为下一轮：未采用，因为它改变了原生 steering 语义，并需要持久队列、
  去重、过期和跨设备 owner 设计。
- 在活跃轮次变化后自动改用 `turn/start`：未采用，因为用户提交的是对确切轮次的 steering，
  静默转换会把上下文和执行时机都改掉。
- 对超时请求自动重放：未采用，因为 `turn/steer` 没有可供浏览器证明未执行的幂等键。
- 首版允许图片和设置覆盖：未采用，因为当前需求是补充文本，而这些能力带来独立的协议和
  生命周期问题。
