# ADR 0013：将线程 Working directory 用作新线程默认上下文与受限文件下载范围

- 状态：已接受
- 决策日期：2026-08-04
- 扩展：[ADR 0002](0002-security-gateway-and-manual-approval.zh-CN.md)、[ADR 0005](0005-thread-and-turn-settings.zh-CN.md)

## 背景

Working directory 表示线程所处的项目上下文。此前新建线程始终回到
`ASK_CODEX_WORKSPACE` 经 bootstrap 提供的默认目录，即使用户正在查看另一个项目中的
线程；这会增加误选目录的机会，也不符合“从当前工作继续”的直觉。

Codex 的 Agent 消息还会使用 CommonMark 链接指向宿主机上的产物或文档。浏览器无法直接
读取这些文件，把绝对路径当作普通链接又会将其拼到 Ask Codex 的公网 Origin 上，并可能
进入浏览器历史和代理日志。解决这一问题不能把网关扩展为接受任意路径的通用文件服务器，
也不能依赖运维人员为每个线程目录维护全局下载根列表。

## 决策

### 新线程默认上下文

- 没有选中线程时，新线程继续使用 `ASK_CODEX_WORKSPACE` 经 bootstrap 提供的默认 cwd。
- 有选中线程时，按以下优先级继承 cwd：与所选 ID 精确匹配的当前线程、Active 或
  Archived 列表中与所选 ID 精确匹配的线程摘要、bootstrap 默认 cwd。不得使用可能由上一个
  线程遗留的通用设置状态作为回退。
- 只继承 cwd。每次打开新线程设置时，sandbox 仍重置为 `workspace-write`；模型和推理强度
  继续遵循各自已有的默认规则。
- `ASK_CODEX_WORKSPACE` 仍只是没有线程上下文时的初始目录，不是文件系统访问边界。

### 受限文件下载

- 不引入 `ASK_CODEX_DOWNLOAD_ROOTS`。每个线程由 app-server 返回的权威 `thread.cwd`
  单独定义该线程的下载范围；浏览器提交的 cwd、路径或线程标识不能建立或扩大范围。
- 只有已完成 Agent 内容中的显式 CommonMark 绝对本地文件链接才可获得下载能力：实时内容
  必须来自 `item/completed` 的 `agentMessage`，历史内容必须来自状态明确为 `completed`
  且包含完整条目的轮次。流式、摘要、失败、中断、用户消息、推理和其他条目默认不签发。
  支持链接末尾的 `:LINE` 和 `:LINE:COLUMN` 定位后缀，但后缀不属于文件名。
- 网关解析消息并向浏览器投影短期、一次性、不透明的 capability ID。下载使用带现有 Bearer
  token 的 HTTP POST；请求只在 URL 路径中携带 capability ID，不接受 path、cwd、
  threadId、请求体或查询参数。宿主机路径和 token 都不得进入下载 URL。
- 每个 capability 在签发时快照权威 cwd 的 canonical 根身份。消费时重新核对该根身份，
  打开并固定匹配的根目录 fd，以该 fd 解析相对目标，再通过目标 `realpath` 和已打开文件 fd
  验证路径与范围，从而拒绝根目录替换、symlink 换指及检查与打开之间的竞态。只允许普通
  文件；目录、设备、FIFO 和 socket 默认拒绝。
- 单文件最多 25 MiB，单个服务器实例最多同时进行 2 个下载，每次活动传输还必须有 2 分钟
  wall-clock deadline。待用 capability、元数据、已知线程 cwd、已完成轮次证据和每条消息可
  签发的链接数都保持显式集合或字节上限。capability 使用短 TTL，消费一次、过期、线程 cwd
  改变、线程删除、app-server 权威状态丢失或服务重启后均不可继续使用。
- HTTP 端点复用既有精确 Origin、Host 和 token 策略，使用固定且不泄露路径的错误响应、
  `no-store`、`nosniff`、`application/octet-stream` 和安全的 `Content-Disposition`，只触发
  下载，不提供文件预览。
- 未获得有效 capability 的绝对本地链接不得退回普通网页链接。外部 HTTP(S) 链接保持原有
  行为。

## 理由

精确继承当前所选线程的 cwd，使“新建线程”默认延续用户正在处理的项目，同时保留无选择
状态下稳定的部署默认值。sandbox 不随之继承，可避免仅因项目上下文延续而无提示扩大执行
权限。

下载能力由已完成的 Agent 内容和 app-server 权威 cwd 共同派生，浏览器只能兑换不透明的
一次性 ID。这样既能导出模型明确指向的工作成果，又不会建立浏览器到任意宿主机路径的
查询接口。范围、文件身份和资源使用均在消费时由网关重新验证。

## 影响

- 从当前线程新建线程时默认保持同一项目目录；从没有选中线程的空状态新建时仍使用部署的
  初始目录。
- 用户可以下载已完成 Agent 消息明确链接的 cwd 内普通文件，文件类型不需要由浏览器预览器
  识别。文件在点击前被删除、移动、换指、变大或超出范围时，下载会失败关闭。
- 当 `thread.cwd` 为 `/` 时，真实范围可以覆盖宿主机上该账户能够读取的绝大部分文件。
  这是允许 `/` 作为真实线程工作目录的明确产品取舍，不通过隐藏的全局根列表改变其语义。
- `ASK_CODEX_TOKEN` 因而必须按宿主机账户密码同等保护：持有 token 且能访问受信 Origin 的
  客户端可以继续线程，并兑换该线程已完成 Agent 链接产生的短期下载能力。
- 多个浏览器客户端看到同一个一次性 capability 时，最先成功消费的客户端使其他客户端的
  同一 ID 失效；重新读取已完成历史可以获得新的短期能力。
- 此能力不是通用文件服务器：它不能列目录、按浏览器路径读取文件、预览任意类型，也不能
  导出没有出现在合格 Agent 内容中的文件。

## 考虑过的替代方案

- 配置 `ASK_CODEX_DOWNLOAD_ROOTS`：未采用，因为不同线程可以有不同 cwd，要求启动时枚举
  所有项目会产生重复配置和漂移；权威 `thread.cwd` 已提供更精确的逐线程上下文。
- 始终使用 bootstrap 默认 cwd 新建线程：未采用，因为用户从当前项目继续时需要重复选择
  目录，并容易在错误项目中启动线程。
- 连同 cwd 一起继承 sandbox：未采用，因为目录上下文与执行权限具有不同风险和生命周期，
  新线程仍应从 `workspace-write` 开始。
- 让浏览器把路径、cwd 或 threadId 发送给下载端点：未采用，因为这会把浏览器输入变成
  宿主机文件选择器，并削弱网关的参数重建边界。
- 将本地链接改为直接 GET 或提供通用预览：未采用，因为路径会进入 URL，预览面会随文件
  类型扩大，而且两者都会使服务更接近通用文件服务器。
