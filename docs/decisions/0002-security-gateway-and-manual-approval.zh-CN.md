# ADR 0002：将网关设为严格的人工审批边界

- 状态：已接受
- 决策日期：2026-07-21
- 追溯记录日期：2026-07-23

## 背景

如果浏览器能够调用任意 app-server 方法或提供不受限制的参数，它实际上就能控制主机端的 Codex 进程。远程访问会放大浏览器遭入侵、代理配置错误以及协议偏移所造成的影响。因此，即使 Ask Codex 是单用户应用，也不能信任浏览器来选择网关的安全策略。

Codex 还会向客户端反向发送审批、结构化问题、权限和征询请求。未知或仅部分支持的请求结构绝不能在无提示的情况下变成权限授予。

## 决策

将服务器用作策略边界，而不是透明代理：

- 维护一份浏览器可调用 RPC 方法的完整允许列表。
- 根据明确允许的字段和经过验证的值重建每个方法的参数；拒绝未知字段。
- 无论浏览器输入什么，在线程创建和恢复时都注入 `approvalPolicy: "on-request"` 和 `approvalsReviewer: "user"`。
- 通过单独的响应策略处理 app-server 审批请求，并对不受支持的细粒度权限和 MCP 征询采取默认拒绝。
- 恢复线程时保留已有的 `externalSandbox`，而不是无提示地将其替换。
- 验证绝对工作目录、执行资源限制、不让 Web 令牌进入 Codex 子进程环境，并且不开放通用文件或终端端点。

每项新开放的协议能力都必须有范围严格的网关策略，以及覆盖允许和拒绝输入的聚焦测试。

## 影响

- 浏览器或 UI 缺陷无法直接绕过配置好的人工审批模式，也不能调用任意 app-server 方法。
- 新 Codex 功能需要对两个请求方向都进行审慎的策略工作。
- 某些上游能力在 Ask Codex 能够安全表达它们之前仍不可用。
- 用户必须审查具有实质影响的请求。这会增加操作成本，但属于产品的核心约束，而非可选模式。

## 考虑过的替代方案

- 转发任意浏览器 RPC 方法和参数：拒绝，因为这会移除网关的安全边界。
- 允许浏览器选择审批策略，包括 `never`：拒绝，因为遭入侵的客户端可能会禁用人工审查。
- 自动批准选定的工具类别：不作为默认方案，因为类别名称无法可靠地反映命令、路径和环境影响。
- 为了与功能更广泛的 Web IDE 对等而开放浏览器终端：推迟处理；这是独立的高风险主机能力，不经过 Codex 审批。
