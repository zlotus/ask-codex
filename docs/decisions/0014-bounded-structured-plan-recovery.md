# ADR 0014：以有界网关快照恢复结构化 Plan

- 状态：已接受
- 决策日期：2026-08-05
- 扩展：[ADR 0012](0012-read-only-connection-recovery.md)

## 背景

Codex CLI 0.146.0 的 `turn/plan/updated` 通知携带一份完整 Plan 快照，而不是步骤增量；
但官方 `Turn`、`thread/read` 和 `thread/turns/list` 结构都不包含 Plan。浏览器休眠、
WebSocket 断开、只读重同步缓冲溢出或切换线程时如果漏掉一次通知，后续官方轮次快照无法
补回它。界面因此可能长时间停在较早步骤，直到下一次完整 Plan 通知抵达后突然跳到后面。

另一方面，Codex 只在实际发出 `turn/plan/updated` 时声明进度。Plan 中某一步耗时很长，
或者模型在一段工作完成后才再次更新 Plan，本身也是正常行为；客户端不能根据工具数量、
墙钟时间或消息内容自行推断步骤已经完成。

## 决策

- 网关对每个合法 `turn/plan/updated` 按 `[threadId, turnId]` 保存最新完整快照，并使用同一
  份逐字段重建结果进行实时广播。只保留 `explanation`、步骤的 `step` 与协议状态
  `pending | inProgress | completed`，不把未知字段透传给浏览器。
- 缓存保持显式资源边界：默认最多 512 条、总计 8 MiB、单条 128 KiB、128 个步骤、
  32 KiB explanation 和 8 KiB 单步骤。一次 RPC 结果最多附加 256 KiB、128 份 Plan，
  重复轮次 ID 不重复克隆。限额必须是正的 safe integer，缓存记录按 UTF-8 序列化大小计入
  标识、key 和固定开销。
- 畸形或超限的实时 Plan 不向浏览器广播原始载荷。网关保存一个有界 tombstone，并发送
  `gateway/resyncRequired`；恢复快照使用 `plan: null` 和 `turn/plan/updated` omission 明确
  表示最新 Plan 无法恢复。缓存中完全没有记录是未知状态，不能证明该轮次没有 Plan，因此
  不添加 `plan` 字段。
- 网关向 `thread/read`、`thread/turns/list`、`thread/resume`、`initialTurnsPage`、
  `turn/start` 结果以及 `turn/started`、`turn/completed` 通知中的轮次附加缓存快照。
  WebSocket 断开、轮次完成和 Codex 子进程重启不清缓存；成功删除线程或收到
  `thread/deleted` 时清除对应记录。
- 浏览器采用三态合并：Plan 对象是权威恢复快照；`plan: null` 是明确的不可恢复或权威空值，
  会清除陈旧 Plan，同时保留相关 omission；缺少 `plan` 表示网关未知或普通稀疏轮次，不改变
  浏览器已有 Plan。浏览器解析器重复执行步骤、文本和总大小限制。
- 只读重同步中，只要轮次快照带有自有 `plan` 字段，该快照就覆盖此前缓冲的同轮 Plan 通知；
  缺少 `plan` 时仍按到达顺序重放缓冲通知。JSONL 和 WebSocket 的到达顺序是状态权威。
  `emittedAtMs` 与 `gatewayReceivedAtMs` 仅保留用于诊断，不参与排序或冲突裁决。
- 缓存只存在于 Ask Codex 网关进程内，不作为新的持久会话数据库。网关进程重启或记录被
  逐出后，未被新通知重新观察到的 Plan 无法从当前 app-server 读取接口重建。

## 理由

网关是同时观察 app-server 实时通知和为浏览器投影只读快照的最窄公共位置。保存完整的
规范化快照，可以让重连、切换线程和读取竞态使用同一状态来源，又不需要调用会改变 owner
的 `thread/resume`，也不需要让浏览器猜测模型进度。明确的未知、不可恢复和可恢复三态避免
缓存未命中被误解释为“没有 Plan”。

## 影响

- 网关已经观察到且仍在预算内的最新 Plan，可以通过后续只读轮次快照恢复；因漏通知造成的
  长期停滞不再只能等待下一次 Plan 更新。
- 如果面板仍停在某一步且没有连接或恢复告警，表示 Codex 尚未发送下一份完整 Plan；客户端
  不会虚构中间步骤。后续多个步骤一起完成仍可能是正常的模型更新节奏。
- 畸形、超限或单次响应装饰预算不足时，界面会显示无法恢复提示，而不会继续把旧 Plan 当成
  最新状态。缓存未知时，已有浏览器快照可以保留，但新页面或另一设备无法重建未持久化 Plan。
- Plan 快照会消耗少量有界网关内存，并增加只读轮次响应的有界体积。达到条目、总字节或
  单次装饰预算时，较早记录或当前响应中的附加内容会降级，而不会无界放大。

## 考虑过的替代方案

- 只依赖 app-server 的轮次读取：未采用，因为当前官方 Turn 和读取响应不含 Plan。
- 只在浏览器保存最后一份 Plan：未采用，因为断线期间遗漏的更新、重新打开页面和另一设备
  都无法通过只读重同步恢复。
- 将 Plan 持久化到新的本地数据库：未采用，因为当前问题只需要跨连接和 Codex 子进程生命周期
  恢复；持久化还需要额外定义版本、清理、隐私和与原生线程的一致性。
- 根据工具完成情况或时间自动推进步骤：未采用，因为 Plan 状态只能由 Codex 的完整通知声明，
  客户端推断会把展示变成另一套不可靠的执行状态机。
- 按 `emittedAtMs` 排序：未采用，因为时间戳只适合诊断，传输到达顺序才是协议处理顺序。
