# ADR 0004：在版本化文档中维护跨设备项目上下文

- 状态：已接受
- 决策日期：2026-07-23

## 背景

开发会跨设备和 Codex 会话持续进行。源代码展示已实现的行为，Git 保存变更，但二者都无法简明说明稳定的产品意图、当前优先级、长期理由和已知风险。把所有这些信息都放入 `AGENTS.md` 会使强制性指令变得冗长、加载成本高，并且容易过时。

自由格式的交接笔记和聊天历史无法保证在每台设备上都可用。不断增长的进度日志或单一决策文件也会逐渐变得嘈杂，并造成频繁的合并冲突。

## 决策

在 `docs/` 下维护一套精简、纳入版本控制的上下文系统：

- `context.md`：记录稳定的目标、非目标、系统形态和约束。
- `progress.md`：记录可替换的当前状态快照、紧接着要做的工作、重要缺口、风险以及实际运行过的检查。
- 在 `decisions/` 下为每项长期架构决策建立一个文件，由 `decisions/README.md` 编制索引，并在其被取代后仍予以保留。
- `ideas.md`：记录尚未决定、未承诺进入路线图的产品候选想法。

仅在 `AGENTS.md` 中保留简短的导航和维护策略。将相关文档与其描述的源代码一同提交，并使用 Git 在设备之间传递完整的交接信息。

## 影响

- 新开发者或新的 Codex 会话无需阅读全部历史或每一份设计记录，即可恢复项目意图。
- 只有实质状态或决策发生变化时才需要更新文档，常规编辑不需要。
- 必须主动精简 `progress.md`，而不能让它变成变更日志。
- 未提交的工作仍然只存在于当前设备，无法仅靠文档实现迁移。

## 考虑过的替代方案

- 将所有上下文放入 `AGENTS.md`：拒绝，因为强制性指令应保持简短且具有规范性。
- 仅依赖提交历史和 issue：拒绝，因为它们无法提供经过整理的当前状态交接信息或稳定的产品上下文。
- 维护一份只追加的进度与决策日志：拒绝，因为它会越来越嘈杂，并造成本可避免的跨分支冲突。
- 依赖聊天历史或助手记忆作为事实来源：拒绝，因为无法保证它们可用、最新或与代码一同纳入版本控制。
