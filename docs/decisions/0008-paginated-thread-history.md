# ADR 0008：新线程使用分页历史契约

- 状态：由 [ADR 0010](0010-app-server-default-thread-history.md) 取代
- 决策日期：2026-07-24

## 背景

Ask Codex 会限制浏览器、网关和 app-server 消息的大小。`thread/turns/list` 可以在
完整轮次过大时降级为摘要，但再次请求同一个完整轮次仍会超过相同上限，因而无法恢复
详情。

Codex CLI 0.145.0 提供实验性的 `thread/start.historyMode` 和
`thread/items/list`。后者只对使用 `paginated` 历史契约创建的线程可用；现有
`legacy` 线程会返回 `thread/items/list is not supported yet`。两种模式的持久化
事件结构不同，且上游没有提供迁移接口。简单修改本地元数据可能造成投影失败或历史
丢失。

在该 CLI 版本中，分页线程还不支持 fork、rollback 和 detached review。Ask Codex
目前没有公开这些操作，但由其他客户端操作同一原生线程时，这项限制仍然存在。

## 决策

- 网关为每个新的 `thread/start` 强制注入 `historyMode: "paginated"`。浏览器不能
  提供或选择该字段。
- 仅以严格受限的方式向浏览器开放 `thread/items/list`：必须同时指定 `threadId` 和
  `turnId`，重新构建所有参数，并将 `limit` 限制为最多 100。
- 客户端按升序手动加载单个轮次的条目页。页面因消息上限失败时，按更小的页面重试，
  直至每页一个条目；不提高既有消息上限。
- 依据 Codex 返回的 `thread.historyMode` 选择恢复路径。`legacy` 线程保留原有的单轮
  完整详情重试；若模式未知，则可尝试条目分页，并在上游明确报告不支持时退回旧路径。
- 不迁移或手工改写现有 `legacy` 线程。它们继续保持 Codex 原生历史的原始契约。

## 影响

- 新线程中的超大轮次可以逐页恢复详情，页面之间按条目 ID 去重，同时保持网关的有界
  消息模型。
- 旧 `legacy` 线程若完整单轮仍超过上限，依然只能显示摘要。单个条目本身超过 1 MiB
  时，分页线程也无法绕过网关上限。
- 分页线程在当前 Codex CLI 中受到 fork、rollback 和 detached review 限制；升级
  CLI 时必须重新核对这些能力和实验性协议结构。
- 被动读取轮次或条目不会取得线程的审批归属；归属仍只由创建、恢复或启动轮次的浏览器
  建立。

## 考虑过的替代方案

- 提高网关消息上限：拒绝，因为这只会推迟同一故障，并扩大浏览器和网关的内存风险。
- 手工把现有线程改成 `paginated`：拒绝，因为没有官方迁移契约，底层事件结构也不兼容。
- 让浏览器选择历史模式：拒绝，因为这会把持久化契约暴露为不必要的客户端策略开关，
  并可能重新创建无法分页的线程。
- 对所有线程无条件调用 `thread/items/list`：拒绝，因为已知的 `legacy` 线程必然失败，
  会制造无效请求和含糊的错误体验。
