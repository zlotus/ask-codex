# ADR 0009：通过临时附件网关提交图片输入

- 状态：已接受
- 决策日期：2026-07-24

## 背景

Codex app-server 的 `turn/start.input` 支持带宿主机路径的 `localImage`，但浏览器既不能
安全地提供宿主机路径，也不应绕过网关直接构造该协议输入。把图片编码成 Base64 并放入
WebSocket 消息，则会很快超过客户端 900 KiB 和网关约 1 MiB 的既有消息上限，并放大
浏览器、网关及 JSONL 通道的内存占用。

Ask Codex 需要在不开放通用文件端点、不接受浏览器路径、也不提高消息上限的前提下，
把浏览器选择的图片交给本地 app-server。上传文件还必须有明确的格式验证、资源配额和
清理生命周期。

## 决策

- 图片二进制通过受现有令牌及 Origin/Host 策略保护的 HTTP 附件端点临时上传，不放入
  WebSocket 消息，也不由浏览器转换成 Base64 协议字段。
- 只接受 PNG、JPEG 和 WebP。网关同时校验声明的媒体类型和文件魔数，不仅依赖文件名或
  浏览器提供的 `Content-Type`。
- 上传成功只向浏览器返回不透明的一次性 `attachmentId`，不返回宿主机路径。浏览器在
  `turn/start` 中只能提交该 ID 及受限的图片 detail；网关消费 ID 后，从私有登记表重建
  官方的 `{ type: "localImage", path, detail? }` 输入。浏览器提供的路径、远程图片和
  其他未支持媒体类型仍被策略拒绝。
- 每张图片最多 10 MiB，每轮最多 4 张。单个 Ask Codex 服务器实例的附件所有者最多保留
  8 个附件、共 40 MiB；底层临时存储全局最多保留 32 个附件、共 64 MiB。这些配额同时
  约束待提交和已租用附件。
- 待提交 ID 的有效期为 10 分钟。附件被轮次消费后成为活跃租约，通常在对应轮次完成、
  提交请求失败、app-server 进入错误状态或 Ask Codex 关闭时删除；另设 6 小时安全
  TTL。租约超过该上限即会删除，即使尚未收到轮次完成通知，以免异常轮次或通知丢失
  无限占用资源。
- 临时目录和文件由服务器创建并控制，目录权限为 `0700`，文件权限为 `0600`。ID 是
  单次使用的进程内能力；Ask Codex 服务重启后，先前返回但尚未消费的 ID 全部失效。
- 保持客户端 900 KiB 以及网关入站、出站约 1 MiB 的既有消息上限。图片上传不会成为
  提高浏览器或网关消息上限的理由。
- MVP 在轮次结束后删除临时文件。Codex 会保留 `localImage.path` 以便原生 UI 编辑历史
  时重新附加图片，因此其他原生客户端在轮次完成后无法通过该路径重新附加原图片。这是
  当前 MVP 的已知兼容性限制；支持该工作流需要另行设计持久附件所有权和回收策略。

## 影响

- 大于 WebSocket 消息上限的图片可以通过有界的 HTTP 上传进入 Codex，同时浏览器无法
  选择任意宿主机文件。
- 一次性 ID、格式检查、数量和字节配额限制了重放、格式伪装和内存或磁盘滥用的影响面。
- 正常轮次在完成后及时回收图片；异常租约也有最终上限，但服务重启后未发送草稿中的
  图片必须重新上传。
- 超过 6 小时仍未完成的极端轮次不保证临时图片继续存在；这是有界资源使用优先于无限
  租约保留的取舍。
- Ask Codex 可以恢复和显示包含图片的历史条目，但其他原生客户端不能依赖已删除的临时
  路径来编辑历史并重新附加原图片。
- 该决策只开放图片输入，不建立通用上传、下载、音频或任意文件访问能力。

## 考虑过的替代方案

- 在 WebSocket 的 `turn/start` 中直接发送 Base64 或 data URL：拒绝，因为这会越过
  既有消息上限，并显著增加序列化和内存成本。
- 接受浏览器提供的 `localImage.path`：拒绝，因为远程浏览器路径不代表可信的宿主机
  文件，而且这会绕过网关的参数重建边界。
- 永久保留所有上传图片：暂不采用，因为需要稳定的存储位置、跨重启索引、引用跟踪、
  用户可见删除语义和有界垃圾回收；这些问题超出图片输入 MVP。
- 将附件端点扩展为通用文件或音频上传：暂不采用，因为每种 app-server 输入都需要独立
  的协议验证、产品呈现和安全策略。
